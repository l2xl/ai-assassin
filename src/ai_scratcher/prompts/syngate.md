# Syngate DAG rules
The syngate items form a tree or, in the general case, a directed acyclic graph (DAG): a condensed record of the analysis and synthesis of the project, which sets the abstraction level and the scope of the AI context, the test coverage and the sustainability a human-controlled review provides. The seed context of an exchange anchored at an item is the chain of its ancestors' statements, root first, then its own, then those of all its descendants in depth, each item once. For the process to stay effective the items follow these rules:
- Every leaf is one simple testable statement about the project. A statement that is not testable as a whole is split into children, each testable or split again.
- A statement is a thesis, not a description: the claim its covering test asserts, named by the test's tag, in the few lines that state it. The detail of how the facility behaves, its cases, rules and rationale, is design and lives in the project's text or markdown files; a statement never repeats what the design file it links to already states.
- Complex behavioural design descriptions are kept out of the items, in the project's text or markdown files, and the item refers to such a file by a root-relative link. The design file is usually referenced by the feature branch item and describes the whole feature behaviour, decomposition rules, guidelines, etc., then the branch item's children define the exact testable requirements. The testable requirements cover the important and strictly testable decisions, the design file holds the idea in general and the definitions that are hard to test.
- A design file is linked from exactly one item, the one whose feature it describes; the items above and below it never link it again, since the seed context already carries the link with that item's statement.
- `sources` are key source files only: the code the statements are about, listed in the structured field so the AI finds and reads it without a search. A design file is never a `sources` entry; it is a link in the statement's text. The two have different roles: a source is what the item constrains, a design file is what the item condenses.
- The project's tests bind to exact items by tags equal to the item UID. No item is created just to refer to a design document or to describe the tests of its parent.
- An intermediate branch exists only for a statement of its own that its children's seed context needs. A branch that merely groups its children under a heading is not created: they go directly under its parent. A description restating the parent's — such as a link to the same design document the parent already links to — marks exactly such a branch and is never added.
- An item's statement is one markdown text, read as a section of one document under its ancestors and detailed by its children. Its first line is the statement's subject — a short noun phrase without articles naming the facility the item defines (`Project edit mode`), or a feature's bare name where its children carry the content — and the outline shows it as the title; the sentence goes on from the next line, after a single line break, with the behaviour the subject has (`instructs the Claude Code connector to call …`), the two lines reading as one sentence in the document. The subject is what the item introduces, never an object of its behaviour (`Immediate interruption facility`, not `Interrupted turn`). The paragraphs past one blank line hold only what the sentence cannot: enumerated cases, limits, exceptions, a design-file link. They never paraphrase the first sentence, and no statement repeats its parent's or its children's.
- No wording is prescribed: the style is the author's, and a new or reworded statement follows the style the tree already uses, so the compiled DAG reads as one concrete document — an article a human reads top to bottom, printable as is.
- Whoever adds or rewords an item rereads the whole branch — the parent and every descendant — and strips what the change made redundant, so the compiled text reads seamlessly.
- An item lists its key source files in `sources`, root-relative, so they enter the seed context at it, above and below it; a file listed by an ancestor is not listed again.
- A UID is short and semantic, composed from its feature's name and what the item adds (`SYNGATE-REVIEW-STATUS`); a numbered suffix is used only where many semantically alike items would make their names long.
